# AutoRotatingView during the system's turn

Status: reference notes (2026-10-20). They describe the code as it is, and the measured behaviour it relies on. The earlier version of this file, with the experiments that led here, is in git history.

## How a turn flows

- **Outermost layer only.** Only the outermost `AutoRotatingLayer` listens to the device and the system. It starts each `AutoRotatingTurn`, and every layer inside takes the same turn and moves on its `TurnClock`.
- **The turn clock.** `TurnClockDriver` animates a count of turns, and progress is how far the count is past the previous turn. A system turn's animation is `SystemTurnAnimation`, which reads `CACurrentMediaTime()` every frame against the turn's `SystemTurnTiming`, so progress matches the system's rotation however late SwiftUI draws its first frame.
- **The turn's timing.** Inside `animate(alongsideTransition:)`, `SystemTurnTiming.measure(in:)` changes a probe view's alpha and copies the animation UIKit gives it: its duration and curve, or spring. A marker animation added in the same transaction reports the begin time in `animationDidStart`. The clock and the `.hold` counter-rotation both use it.
- **Nested layers.** A nested layer takes the outermost turn in the same layout pass (`currentTurnState`) and stores it in `onChange`. It turns relative to the enclosing content (`ContentRotation`, `LayerTurn`).
- **`.hold`.** `RotationLockingHost` keeps the content at its old size and adds a counter-rotation inside `coordinator.animate(alongsideTransition:)`, so it starts in the system's own transaction. When the counter-rotation ends, it hands over the new frame and removes the counter-rotation in one transaction.

## Measured behaviour the code relies on

These were measured on the iPhone 18 Pro and iPhone Duo simulators, iOS 27.0 and 27.1. They are what the code's shorter comments refer to.

| Fact | Where it matters |
| --- | --- |
| SwiftUI lays the interface out at its new size before state set in `viewWillTransition` reaches the view. That layout has the new size and safe area but the old rotation. | The outermost layer keeps its frame after each layout in `onChange(of: frame)`, and `viewWillTransition` reads it (`announcement.frame`) before that layout. A UIKit view's `safeAreaInsets` would miss SwiftUI-only insets such as `safeAreaInset`. |
| Inside `animate(alongsideTransition:)`, UIKit gives a view's change a `CABasicAnimation` with control points (0.42, 0), (0.58, 1), the coordinator's `transitionDuration` (0.3 s a quarter turn, 0.6 s a half turn) and `beginTime` 0. The window's own `bounds.size` and `position` animations have the same timing. `completionCurve` is `.easeInOut`. | `SystemTurnTiming` copies the animation rather than assuming the curve. |
| The system's animations begin when the transaction is committed, 10 to 85 ms after `viewWillTransition` in the simulator. A clock started at `viewWillTransition` ran up to 0.35 of the turn ahead of the window's animated bounds. Timed from the marker's `beginTime`, it was within 0.006 at every frame. | `SystemTurnTiming.beginTime`; progress is 0 until it arrives. |
| A half turn has no window animation in the app, but a change inside it still gets UIKit's animation with the half turn's duration. | Half turns are measured the same way. Their screen rotation runs outside the app, so its start isn't measured directly. |
| `coordinator.transitionDuration` already doubles for a half turn. | Turn duration everywhere. |
| A half turn's `targetTransform` doesn't say which way it turns. The system always turns it the positive way. | `Angle(interfaceTurn:)`. |
| The transition's completion can run as soon as a half turn starts. | The host releases on its counter-rotation's own `CATransaction` completion. |
| The device orientation notification can arrive after the system's turn to that orientation has started. | `announcement.isSystemTurning(to:)` in `deviceOrientationDidChange`. |
| After a device turn to an orientation in the effective mask, the system starts its turn a few milliseconds later. An iPhone without a Home button doesn't turn to upside down even when the mask allows it, and no API reports that. The device orientation notification is posted inside the system's rotation animation when it turns: `UIView.inheritedAnimationDuration` is 0.3 (0.6 for a half turn) there, and 0 when the system doesn't turn. Measured on the iPhone 18 Pro (iOS 27.0) and the iPhone Duo's outer screen (iOS 27.1). On the iPhone SE (3rd generation, iOS 27.0), which has a Home button, the system turns to upside down, and the notification has 0.3 for a quarter turn and 0.6 for a half turn. Not measured before iOS 27. | A `.system` layer changes in the notification when it has an inherited animation (the `.device` turn), as the change made later, inside `animate(alongsideTransition:)`, looked worse on a device. Other layers wait for the system's turn. Content turns on its own at once for an orientation outside the mask, or for upside down on an iPhone when the notification has no animation (`isSystemRefusing`). |
| The hinge reports a new screen before the interface moves there, while the scene is still on the old screen with its orientation. 55 to 120 ms later the scene's `effectiveGeometry` changes (KVO), on the new screen with its orientation, and about 2 ms after that the interface moves with an unanimated transition (`isAnimated` false, duration 0). Measured on the iPhone Duo simulator, iOS 27.1, unfolding and folding in portrait and landscape. Folding in landscape, a second unanimated transition can follow, turning to the other landscape. | A layer's state keeps the screen it's on (`TurnState.screen`), and moves when its scene's screen differs (`moveToSceneScreen`), at the KVO or, if it comes first, the transition. The hinge isn't used. An unanimated transition that finds the content already in the scene's orientation has nothing to turn. Any other, such as the second one after folding in landscape, is a turn of no duration, so the layers inside take it too. |
| On the iPhone Duo (iOS 27.1) a rotation's coordinator reports 0.3 s and `isAnimated`, as on the iPhone 18 Pro, and `effectiveGeometry` already has the new orientation in `viewWillTransition`. | `SystemTurnTiming` works the same on both. |
| `toolbarVerticalEdge` lags the turn by one layout pass. | `TurnStart.systemBar` keeps the bar from before the turn until the new measurement arrives. |
| Inside held content, the scoped `animation(_:body:)` doesn't animate. `animation(_:value:)` does. | `autoRotatingHeldTurnAnimation` docs. |
| In a reader whose layout direction differs from the app's, SwiftUI names system UI in a corner for the reader's direction but the rounded corners for the app's. | Corner insets are read in the caller's direction. |
| On a device (iPhone 18 Pro, iOS 27.0.1), the system's turn starts about 1 ms after the device orientation notification, so `.system`'s new rotation is first drawn inside UIKit's rotation animation. The window has no transform: the system turns the display while the window's bounds animate. Core Animation animates the content layer's rotation and position separately, and SwiftUI places a turned layer by its corner, so the content's centre drifts about 140 pt off the window's centre mid-turn and the animated bounds crop it. Neither a scoped `transaction` without animation nor turning a zero-size frame at the centre changed it. | `FUCounterRotationStyle.system` docs: a known limitation; `.hold` avoids it. |
| `UIApplication.supportedInterfaceOrientations(for:)` returns the Info.plist value (all four in the example app on the iPhone 18 Pro simulator), not what the device allows. With upside down in it, the iPhone 18 Pro still doesn't turn to upside down. | `FUInterfaceOrientation.systemOrientations(in:)` intersects the scene or app delegate's mask, or that value, with the top full-screen view controller's, and honours `isInterfaceOrientationLocked`. Upside down on an iPhone stays uncertain. |
| A view controller SwiftUI shows in a navigation stack gets a stand-in transition for a rotation: identity `targetTransform`, not animated, duration 0, with the scene already in the new orientation. The window's root view controller gets the system's own transition, also under a full-screen cover. Measured on the iPhone 18 Pro simulator, iOS 27.0. | `InterfaceRotationAnchorView` adds its view controller to the window's root. The host is still placed by SwiftUI, so `.hold` inside a navigation stack doesn't hold. |
| A layer's `onAppear` runs before its `InterfaceRotationAnchorView` moves to a window. | The layer reads its own scene from `onInterfaceRotation(_:windowScene:)`, and until then uses the app's window scene only when there's exactly one. |
| `ConcentricRectangle` and `ContainerRelativeShape` resolve against the unturned container. Setting a container shape inside `AutoRotatingView` would change the shape of style backgrounds even when nothing turns. | `AutoRotatingGeometryProxy.concentricCornerRadii`; no `containerShape` is set. |

## Known heuristics

The review on 2026-10-20 listed the values that aren't derived from the system. The 0.1 s and 0.3 s fallbacks, the hard-coded curve and start time, the foreground scene and Info.plist orientations have since been replaced. What's left:

- `isSystemRefusing` relies on the measured, undocumented fact that the system posts the device orientation notification inside its rotation animation. It's used only for upside down on an iPhone, and wasn't measured before iOS 27.
- On iPad, `systemOrientations(in:)` ignores the top view controller while the app multitasks: when it doesn't require the full screen and its Info.plist has every orientation, as `supportedInterfaceOrientations` documents. Tested as a rule and on the iPad Pro 11-inch simulator (iOS 27.0), but not with an app whose own view controller limits its orientations.
- Before a layer is in a window, it uses the app's window scene only when there is exactly one, and otherwise has no scene orientation until the window arrives.
- A half turn's screen rotation runs outside the app. Its timing is taken from the animation UIKit gives the app's own changes, which begins at the same commit, but the screen itself wasn't measured.
- The 0.3 s default `animation` is a chosen default. It doesn't double for half turns. It could instead follow the last `SystemTurnTiming` the app saw, which would match the system after the first turn but not before it.
- Out of scope for the review: the system bar sizes in `SystemBarGeometry`, the 1° tolerance in `FUInterfaceRotation(exactly:)` and `Angle(interfaceTurn:)`, and the half turn's direction.
